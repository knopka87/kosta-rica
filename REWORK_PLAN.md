## 1. Цель

Сейчас это **справочник**: набор длинных страниц, которые надо читать. Нужен **навигатор**: экран, который в любой момент поездки отвечает на три вопроса без единого тапа —

1. **Где я сейчас** и что это за этап.
2. **Что будет дальше** и через сколько.
3. **Что надо сделать прямо сейчас** (и чего нельзя забыть).

Всё остальное — контент, карты, фразы, бюджет — обслуживает эти три вопроса.

Критерий, по которому меряем успех: **нужное действие достигается с главного экрана не более чем за 2 тапа, в самолётном режиме, одной рукой, на солнце.**

## 3. Архитектурное решение

**Остаёмся на статическом генераторе + vanilla JS + Capacitor.** Никакого React/Compose: для одного маршрута это проще, надёжнее в офлайне и уже работает. Но переходим от «набора больших markdown-страниц» к **data-driven модели**.

Ключевой ход: **`trip.json` как единственный источник правды по маршруту.** Из него генерируются дашборд, страницы этапов, `calendar.ics`, навигация, поисковый индекс и быстрые действия. Статьи (правила, еда, лайфхаки, покупки) остаются Markdown и подключаются к этапам по ссылкам, а не копированием.

### 3.1 Схема `trip.json`

```jsonc
{
  "version": 1,
  "trip": {
    "id": "cr-2026",
    "title": "Коста-Рика 2026",
    "homeTz": "Europe/Kirov",
    "startAt": "2026-10-30T07:27:00+03:00",
    "endAt": "2026-11-10T05:07:00+03:00"
  },
  "segments": [
    {
      "id": "ist-panama",
      "num": 4,
      "kind": "flight",              // flight | train | stay | transfer | layover | window
      "title": "Стамбул → Панама",
      "icon": "✈️",

      // Абсолютные моменты. Устройство может быть в любом поясе — сравнение по epoch.
      "startAt": "2026-10-31T13:50:00+03:00",
      "endAt":   "2026-10-31T20:05:00-05:00",
      "fromTz": "Europe/Istanbul",
      "toTz":   "America/Panama",

      "from": { "code": "IST", "name": "Стамбул", "terminal": null },
      "to":   { "code": "PTY", "name": "Панама", "terminal": null },

      "carrier": "Turkish Airlines",
      "number": "TK 903",
      "booking": { "private": true, "ref": "doc:tickets#tk" },   // → в зашифрованный блок

      "baggage": { "checked": "2 места", "cabin": "1 место", "note": "багаж НЕ прокидывается на Copa" },

      "alerts": [
        { "level": "critical", "text": "В Панаме забрать багаж и пройти таможню — билеты разные PNR" }
      ],

      "actions": [
        { "text": "Заполнить миграционную карту Панамы на борту", "when": "before-end" },
        { "text": "Перевести часы на UTC−5", "when": "at-end" }
      ],

      "links": [
        { "label": "Пограничный контроль Панамы", "href": "pravila.html#panama-border" },
        { "label": "Фразы на испанском", "href": "phrasebook.html#airport" }
      ],

      "planB": "Если рейс задержан и стыковка в Панаме горит — Copa CM 342 следующий в 17:40.",
      "content": ["plan-poezdki.md#31-oktyabrya", "lifehacks.md#nochnoy-perelyot"]
    }
  ]
}
```

**Правила схемы:**

- `startAt`/`endAt` — **всегда** ISO-8601 с явным offset. Никаких «локальных» дат и `HH:MM`-границ. Текущий сегмент = тот, чей `[startAt, endAt)` содержит `Date.now()`. Пояс устройства перестаёт влиять в принципе.
- `fromTz`/`toTz` (IANA) — **только для отображения**: формат локального времени в точке и домашнего времени (Киров) рядом, DST-safe.
- `booking.private: true` — поля не попадают в публичный HTML; рендерятся только после разблокировки, из расшифрованного фрагмента.
- `content` — ссылки на секции markdown, не копии. Один факт живёт в одном месте (лечит D13).
- `calendar.ics` генерируется **из `segments`**, `CALENDAR_EVENTS` удаляется (лечит D8).
- `links[].href` проверяется link-checker'ом на этапе сборки (лечит D7).

### 3.2 Валидация на сборке

`build.py` падает, если:
- интервалы сегментов пересекаются или оставляют дыру > 15 мин без явного `"gap": true`;
- `endAt <= startAt`;
- `tz` не резолвится в IANA-базе;
- якорь из `links[]`/`content[]` не существует в собранных страницах;
- сегмент без `title`/`kind`/`startAt`.

Это дешёвая страховка: один неверный offset в JSON — и в поездке приложение показывает не тот этап.

## 4. Информационная архитектура

### 4.1 Режимы главного экрана

Главный экран — не каталог, а **контекстный дашборд**, который меняет форму по фазе поездки:

| Режим | Когда | Что сверху |
|---|---|---|
| **Before trip** | до `trip.startAt` | обратный отсчёт, прогресс сборов и дел, «осталось доделать», документы |
| **In transit** | сегмент `kind ∈ {flight, train, transfer, layover}` | текущий сегмент, **«до следующего события — N ч M мин»**, номер рейса/вагона, терминал, багажное правило, 3–5 действий, критические алерты |
| **At destination** | сегмент `kind = stay` | день в Тамариндо: погода, что запланировано, что рядом, бюджет за день, карта |
| **After trip** | после `trip.endAt` | журнал, экспорт, расходы, фото |

Порядок блоков в режиме **In transit** (самый нагруженный):

```
┌─ статус: офлайн/онлайн · данные актуальны на ... · 🔒 заблокировано
├─ СЕЙЧАС: ✈️ TK 903 Стамбул → Панама        [крупно]
│  прилёт 20:05 (04:05 по Кирову) · осталось 3 ч 20 мин
├─ ⚠️ Багаж забрать в Панаме — билеты разные PNR   [критический алерт]
├─ СДЕЛАТЬ СЕЙЧАС  (3–5 чекбоксов, из segment.actions)
├─ ДАЛЬШЕ: 🌃 Ночь в Панаме, заселение ~21:30
└─ [🔒 Документы] [🗺️ Карта] [💬 Фразы] [💰 Траты]   [крупные кнопки]
```

Полный маршрут, статьи и справочники — на втором уровне, через «Маршрут» и поиск.

### 4.2 Навигация

- **Mobile (основной сценарий):** нижняя панель из 4 пунктов — **Сейчас / Маршрут / Инструменты / Документы**. Таргеты 48×48 px, всё в зоне большого пальца. Sticky action bar на страницах этапов.
- **Desktop:** сохраняем topbar + боковое оглавление.
- **Глобальный поиск** по локальному индексу (генерируется на сборке, ~100–200 КБ JSON): заголовки, секции, ключевые факты, номера рейсов. Работает офлайн, открывается с любого экрана (лечит D15).

### 4.3 Шаблон этапа

Каждая страница этапа приводится к единой структуре, сверху вниз — от «что делать» к «подробности»:

1. **Заголовок + где/когда** (видимый H1 — лечит D2), баннер «Вы здесь» / «Этот этап впереди».
2. **Цель этапа** — 1–2 предложения.
3. **Таймлайн** — события с временем в двух поясах, маркер «сейчас».
4. **Чек-лист** — действия этапа, отметки сохраняются.
5. **Билеты, адреса, контакты** — приватное за замком, публичное сразу.
6. **Карта** — точки этапа.
7. **Еда / покупки / правила** — только релевантное этапу, ссылками.
8. **План Б** — что делать, если сорвалось.
9. **Подробности** — всё остальное в аккордеонах, свёрнуто (лечит D12).

## 5. Что берём из практики travel-приложений

### 5.1 Нормативные опоры

Решения, на которые мы ссылаемся как на обязательные, подкреплены первичными источниками:

| Решение в плане | Норма / спецификация |
|---|---|
| Local-first writes, локальное хранилище как canonical source of truth (раздел 6) | [Android Developers — Build an offline-first app](https://developer.android.com/topic/architecture/data-layer/offline-first): «The local data source is the canonical source of truth… Write any updates to the local data source first» |
| Таргеты: формальный минимум 24×24 px (раздел 8) | [WCAG 2.2 SC 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) — Level **AA**, «at least 24 by 24 CSS pixels» |
| Фактический размер основных контролов 44–48 px (раздел 8) | [WCAG 2.2 SC 2.5.5 Target Size (Enhanced)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) — Level **AAA**, «at least 44 by 44 CSS pixels». Берём как цель для главных кнопок, не как conformance-заявление по всему сайту |
| Precache, селективное кэширование, Range-отдача PMTiles (раздел 6) | [MDN — Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API), интерфейсы `Cache` / `CacheStorage` |

### 5.2 Продуктовые паттерны (pattern inspiration)

Это не нормы и не измеренные практики, а ориентиры из известных travel-приложений. Приняты потому, что ложатся на наш сценарий, а не потому, что кем-то доказаны:

- **Next-event card над сгибом** (TripIt Go mode, Wanderlog): в день перелёта пользователь не «просматривает» — он управляет логистикой под давлением времени. Интерфейс должен обслуживать это состояние без навигации.
- **Таймлайн дня с визуально различимыми типами карточек** — рейс, отель, активность выглядят по-разному и сканируются взглядом.
- **Offline destination package** (Google Maps offline, Maps.me): карта, точки, брони, фразы, экстренные контакты, чек-листы — одним явным скачиванием с размером и прогрессом, а не фоновым сюрпризом на 40 МБ.
- **Часы двух поясов** — местное и домашнее время рядом на каждом событии. При UTC−9 от Москвы это не украшение, а необходимость.
- **SOS-экран**: экстренные номера Коста-Рики/Панамы, страховка, посольство — один тап, работает офлайн.
- **Мультивалютный трекер трат** (TravelSpend) — у нас уже есть, остаётся довести до одного тапа с дашборда.
- **Freshness-индикатор** — «данные обновлены тогда-то», чтобы офлайн-кэш не выдавал себя за свежие данные.

Обзорные материалы, с которых начинали: [Tours and Attractions Mobile Applications](https://www.altexsoft.com/blog/tours-and-attractions-mobile-applications-best-practices-and-examples-of-ta-apps/), [Offline Mobile App Design](https://leancode.co/blog/offline-mobile-app-design), [Offline Functionality For Accessible Travel Apps](https://nextpageit.com/blog/accessible-travel-offline-functionality-for-remote-destinations) — вторичные блоги, нормативной силы не имеют.

## 6. Офлайн и хранилище

### 6.1 Офлайн

- **App shell + критический контент** (этапы, чек-листы, фразы, экстренные контакты, зашифрованные документы) — precache, это единицы мегабайт.
- **PMTiles 40 МБ** — отдельной кнопкой «Скачать офлайн-карту» с размером, прогрессом и версией. Cold load не тянет ни байта карты до явного действия (лечит D10).
- **Freshness**: на дашборде — время последнего успешного обновления и статус сети.
- **Local-first writes**: все пользовательские записи пишутся локально и только потом (если появится синк) уходят наружу.

### 6.2 Хранилище

Единый **versioned storage adapter** поверх `localStorage`:

- одна точка входа, схема с номером версии, транзакционные миграции с rollback-снимком;
- автоматические versioned snapshots внутри хранилища (N последних) + **явный one-tap backup / restore** — в вебе бесшумная запись файла без user gesture невозможна, поэтому обещаем именно one-tap, а не «автоэкспорт»;
- обработка quota exceeded и повреждённых записей (не падать, а чинить из снимка);
- **IndexedDB — только под блобы** (фото в журнале), где `localStorage` упрётся в 5 МБ;
- в Android — scheduled backup в app-private storage через Capacitor-адаптер;
- миграционные тесты на реальных дампах текущих ключей (`cr:list:v1:*`, `cr:budget:v2`, `cr:journal:v1`) — потеря журнала поездки недопустима (лечит D11).

## 7. Приватность

- Оставляем AES-256-GCM + PBKDF2 (210 000 итераций).
- **Удаляем `docs/meta.json`.** Пароль проверяется расшифровкой `manifest.bin` — AES-GCM аутентифицирует сам (лечит D9).
- **Одинаковое публичное сообщение** на неверный пароль и на повреждённый блоб — никаких подсказок.
- **Exponential UI backoff** после нескольких попыток.
- **Auto-lock** по таймауту и при уходе в фон; очистка ключевого материала и приватного DOM при блокировке.
- Приватные поля **не попадают в HTML и кэш в открытом виде** — рендерятся только после разблокировки.
- **Android:** ключ через Keystore + biometric unlock.
- **Threat model пишем честно:** на статическом хостинге это барьер от случайного доступа по ссылке и от любопытных, не замена серверной авторизации. От офлайн-брутфорса слабой парольной фразы защиты нет — UX обязан требовать длинную passphrase.

## 8. Доступность и качество

**Conformance target — WCAG 2.2 AA**, с поправкой на реальные условия (солнце, одна рука, спешка):

- таргеты: обязательный уровень — SC 2.5.8 (AA), то есть **24×24 px либо допустимое spacing-исключение**; для основных мобильных действий держим продуктовую цель **44–48 px**. Это не заявление о полном AAA — SC 2.5.5 берём точечно, как ориентир, а не как уровень соответствия;
- контраст: AA на тексте, повышенный на критических алертах; проверка в режиме яркого солнца;
- видимый focus, `prefers-reduced-motion`, корректные лейблы для скринридера;
- тёмная тема (половина перелётов ночью) и крупный шрифт;
- работа одной рукой: всё важное — в нижней трети экрана.

## 9. Фазы

### Фаза 0 — остановить кровь (приоритет, независимо от остальной архитектуры)

| Задача | Лечит |
|---|---|
| Детерминированный порядок скриптов: seed генерируется **до** исполняемых скриптов, общие скрипты с `defer`. **Дополнительно** — guard на отсутствие собственного mount в каждом модуле (защита от будущей рассинхронизации шаблонов) | D1, D3 |

| **Откатить WIP-разметку главной и `app.js`** до коммита, главную переделывать уже по новой дизайн-системе. Стилизовать DOM, который мы выбросим в фазе 3, — потерянная работа. Новые route steps и Capacitor scaffolding сохраняем | D4 |
| Убрать дублирующий countdown | D5 |

**Критерии приёмки фазы 0:**
- zero uncaught page errors на **всех** генерируемых страницах;
- ровно один countdown-таймер;
- видимый единственный H1 на каждой странице;
- `[data-steps-current]` и `[data-step-now]` работают;
- link-check всех генерируемых якорей зелёный;
- cold load не скачивает PMTiles до явного действия.

### Фаза 1 — модель данных
`trip.json` + схема + валидация на сборке + генерация `calendar.ics` из сегментов + удаление `CALENDAR_EVENTS`. Тесты границ сегментов: фиксированные моменты **за секунду до, ровно на и через секунду после** каждой границы × `TZ=` для Кирова, Москвы, Стамбула, Панамы, Коста-Рики. Прод-код инъекции часов не получает — тесты гоняют фиксированные входные моменты.

### Фаза 2 — дизайн-система и shell
Токены (цвет, типографика, отступы, радиусы, тени), компоненты (карточка события, алерт, чек-лист, таймлайн, кнопка действия, аккордеон), mobile-first shell с нижней панелью, тёмная тема.

### Фаза 3 — контекстный дашборд
Четыре режима, Now / Next / Do now / алерты / быстрые кнопки, статус офлайна и блокировки.

### Фаза 4 — шаблон этапов и рерайт контента
Приведение 11 этапов к единому шаблону, устранение дублей (D13), сворачивание справочного объёма в аккордеоны (D12), локальный поиск (D15).
**Правило рерайта:** источник правды — фактические билеты, брони и проверенные заметки (`plan-poezdki.md`, `lifehacks.md`, `pravila-zakony.md`, `eda.md`, `chto-kupit.md`). `step-01..11.md` помечаются как **неподтверждённый черновик** и источником не являются (D14). Каждое критическое утверждение (время, терминал, багаж, деньги) получает provenance и дату последней проверки.

### Фаза 5 — офлайн, storage, приватность
Офлайн-пакет с прогрессом, versioned storage adapter + миграции + one-tap backup/restore, удаление verifier и остальное из раздела 7.

### Фаза 6 — Capacitor
Адаптеры storage/Keystore/biometric, вшитый контент, проверка что SW не мешает.

### Фаза 7 — QA
Реальный Android + airplane mode + симуляция часовых поясов по всему маршруту + ревью пароля и приватности + проверка одной рукой на солнце.
